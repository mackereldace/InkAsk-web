# 大 PDF 与嵌套便签：实测与加载方案

2026-11-12，本机 macOS、Chromium IAB，使用本地模拟模型，无外部 AI 请求。目标负载按用户要求：每页 5 个根便签，每个包含根、子、孙共 3 层，即每页 15 条便签。每条一问一答，回答约 600 字并含公式、引用，子/孙分别保存 2/4 条祖先问答。页面原生文字已缓存，避免把 OCR 开销混入便签负载。

结论：当前页面画布和回答 DOM 已按阅读位置控制，不会同时排版所有嵌套回答。大文档的主要剩余风险是整包加载、整包保存与重复保存祖先历史。基础优化能明显降低一次追问的开销，但当前版本仍不能宣称任意大 PDF、任意数量便签都有固定内存占用。

## 测量结果

| 负载 | 解压后的项目 JSON | ZIP 项目包 | 首次导入至阅读区可见 | 跨约 20 屏后的画布 / 根便签标记 | 进入一篇回答 |
| --- | ---: | ---: | ---: | --- | ---: |
| 500 页 / 7500 条便签 | 41.5 MB | 1.18 MB | 449 ms | 5 / 25 | 288 ms |
| 2000 页 / 30000 条便签 | 166.5 MB | 4.71 MB | 1724 ms | 5 / 25 | 316 ms |

只挂载 1 篇回答正文，测试回答约 259 个 DOM 元素。未打开的子回答没有执行 Markdown / LaTeX 排版。500/2000 页目前仍保留 500/2000 个轻量页面占位，约 1800/6300 个总 DOM 元素；画布初始 3 张，滚动后约 5 张。

2000 页样本初次导入观察到约 462 MiB JS 堆，滚动稳定后约 155 MiB。在该样本中对一篇回答再发起短追问：

| 同一类本地短追问 | 基础优化前 | 基础优化后 |
| --- | ---: | ---: |
| 回答生成完成 | 1694 ms | 1164 ms |
| 生成至最终保存完成 | 2914 ms | 1533 ms |
| 保存完成观察点的 JS 堆 | 1591 MiB | 443 MiB |

优化后从已保存资料重新打开至阅读区可见约 369 ms，打开及滚动不重写项目。单便签拷贝的 Node 独立基准（5 次采样中位数）从 9.23 ms 降到 1.19 ms；此基准只测对象拷贝，不包含 DOM、归档或数据库。

这些是本机单轮 UI 观察，不是固定峰值、帧率或所有机器的承诺；未强制浏览器 GC。原始计数保留在 [reader-performance-results.json](reader-performance-results.json)。累计 JS 时间该轮为 351/563 ms，受采样窗口、GC、页面状态影响，不能据此宣称 CPU 已全面降低。真实模型的长时间生成、多图片扫描件和 Safari 的同等大负载仍须单独重复测量。Safari 本轮只完成普通 PDF 阅读、扫描页检测和滚动的功能验收。

## 本轮已经实现

- 每张显示/截图画布上限 8 Mi 像素、单边 8192；普通 A4/DPR2 不降采样，超限才降低位图分辨率，文字层与选区坐标不变。引用截图直接渲染选区，不先分配全页中间位图；OCR 返回实际渲染比例以保持定位准确。
- PDF 只渲染阅读位置附近页面；根便签按页索引，回答只渲染当前层，子便签继续显示为原处入口。
- 图片按稳定组件维护 URL，引用截图按需生成；引用缓存最多 12 项，关闭预览释放组件的 Blob URL。
- 流式内容只复制当前便签与消息，保持其他便签和继承历史引用；页面状态条目仍隔离，避免污染保存快照。
- 保存请求串行，同版本合并，排队旧版本替换为最新版本；队列尾屏障不保留已保存项目对象。生成中常规检查点延长到 5 秒，结束、切换资料和页面进入后台仍立即保存。
- 保留保存入口的同步深快照，移除存储准备阶段第二次整包深拷贝；失败事务保留原项目。
- 阅读位置和缩放使用独立本机偏好，不增加内容修订号或修改时间；已保存资料打开时不执行无意义的全量保存。

## 已确定的后续方案

### P1：便签分行存储、按阅读分支加载

这是首先应做的结构改动，优先于增加渲染特效。

1. IndexedDB 新增项目头、便签索引、便签正文/消息表。索引保留文档 ID、页码、父便签/父回答 ID、标题、坐标、消息版本和计数；建立文档+页码、父便签+父回答索引。
2. 初次打开只取项目头和当前页附近的根便签索引。点击便签后只载入当前回答及必要的祖先链；其余回答内容不进入内存。正文使用带字节上限的 LRU，例如 32 MiB 起步，实际阈值由同一负载复测确定。
3. 流式生成只更新正在生成的消息行及相关索引，事务同时维护修订号、资料更新时间；检查点不再序列化整个 166 MB 项目。
4. 祖先历史改为不可变消息版本或内容哈希引用，而非重复文本。不能只引用会被重试覆盖的当前消息 ID，否则将破坏已有分支的历史隔离。每个分支必须继续还原创建时的精确历史。
5. 附件字节保持独立存储，仅加载当前回答需要的附件；正文淘汰时同步释放图片 URL。归档导出按一致修订快照补齐正文及历史，确保便签、父子关系、来源和图片完整。

迁移要求：按项目惰性迁移 v2 整包记录；逐项核对数量、引用及必要校验后，事务提交新项目头。新记录验收前保留旧记录，失败可继续使用旧资料。不能为性能直接删掉现有历史或改变备份语义。

### P2：真正的页面窗口与文本提取调度

- 当前数千个轻量占位仍随页数线性增长。升级为基于页尺寸前缀和的窗口，仅保留可见页及前后预取窗口的 DOM；纵向和横向使用同一坐标映射，跳页、返回阅读位置、引用定位和选区坐标保持一致。
- 先提取当前页和相邻页文字，其余页在空闲时分批提取/建立检索索引；按页保存，避免每提取一页都复制整个便签树。全文检索结果须明确尚未索引的范围。
- 长文档检索/归档解析移到 Worker，并采用有界批次。画布像素、附件解码和页面预取均设置内存预算；仅在渲染任务结束后清理 PDF 页面资源。

### 完成标准

仍使用这两组样本，另加多图片扫描件，分别在 Chromium 和 Safari 复测：首次打开、冷/热进入回答、连续快速滚动、5 分钟流式生成、切换资料、取消生成、关闭后恢复、导出再导入。记录多轮中位数与高分位数、长任务、画布数量、常驻/最高观测内存、写入的行数/字节；验证三层历史、旧数据迁移和失败回滚完整。

目标是让已加载正文、渲染节点和每次检查点的数据量跟当前阅读窗口及修改量相关。只有这些指标在增加到 30000 条便签后仍受预算约束，才将“大文档按需加载”标记为完成。当前 `.inkask` 解压总量仍限制为 512 MiB，不能用压缩包只有几 MB 推断内存或备份容量没有限制。

## 重现

```sh
node --import tsx scripts/reader-stress.mts --pages 500,2000 --out /private/tmp
```

生成的 `.pdf` / `.inkask` 及统计位于 `/private/tmp/inkask-reader-stress-*`，不提交大样本或浏览器资料。纯拷贝基准数据见 [project-edit-benchmark.json](project-edit-benchmark.json)。
